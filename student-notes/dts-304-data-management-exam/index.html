LESSON 1 · INTRODUCTION TO DATABASES

1 · Data, management + databases

1.1 Data → management → database

DataFacts and numbers used to analyse something or make decisions. "raw facts and figures"
→
ManagementPlanning, organising, leading and controlling an organisation's resources to reach its goals efficiently.
→
DatabaseAn organised, electronic collection of data, usually kept and accessed through a computer system.
Formal definition (learn this one)A database is a shared collection of logically related data (and a description of this data), designed to meet the information needs of an organisation.
Logically related data =
  • Entities → tables
  • Attributes → fields
  • Relationships between them
These three make up the ERD (§7).
Metadata / system catalog"Data about data": the description of the data stored in the database. It is what gives a database its structure, and it enables program–data independence.

1.2 The 5 Cs of data management

Five guidelines for building data products:

Consent
Clarity
Consistency
Control
(+ transparency)
Consequences
(+ harm)
"Can Class Continue Calmly, Captain?" Consent, Clarity, Consistency, Control, Consequences. "Classification" is NOT one of them (asked in the MCQs).

1.3 Relational database

Groups data using the common attributes found in the data, so the "clumps" of data are easy to understand. The grouping is called the schema. The relational model is the main choice for financial records, logistics, personnel data and more.

Draw it like this (a relation = a table) 
         STUDENT  ← relation (table)
 ┌────────┬─────────┬────────┐
 │ RegNo  │ Name    │ Dept   │ ← attributes (columns)
 ├────────┼─────────┼────────┤
 │ 241001 │ Ada     │ SEN    │ ← tuple (row / record)
 │ 241002 │ Musa    │ CYB    │
 └────────┴─────────┴────────┘
   ↑ primary key: unique, not null
Relation = table · tuple = row · attribute = column · domain = the allowed values for a column · tables are linked by keys.
Why the industry mostly uses it
  • Simple: everything is a table, which is easy to understand.
  • SQL: one standard, non-procedural language.
  • Integrity: primary and foreign keys keep data correct and linked.
  • Flexible queries: join any tables on common attributes.
  • Data independence, and widely supported (MySQL, Oracle, SQL Server).

2 · File-based systems vs the database approach

2.1 File-based system

File-based systemA collection of application programs that perform services for end users (e.g. reports). Each program defines and manages its own data. The data is stored in files with no metadata, so there's no organising structure.
vs
DatabaseA self-organising collection of integrated records. Its metadata gives it structure, and all programs share it.
FILE-BASED                         DATABASE APPROACH
Sales prog ──► Sales files         Sales prog ──┐
Lease prog ──► Lease files         Lease prog ──┼──► DBMS ──► one shared DB
Staff prog ──► Staff files         Staff prog ──┘         (+ metadata)

2.2 Five limitations of the file-based approach

1 · Separation + isolationEach program keeps its own data, so users of one program may not know about useful data in another.
2 · DuplicationThe same data is held by different programs, which wastes space and can leave different values or formats for the same item.
3 · Data dependenceThe file structure is defined in the program code, so changing it means changing the programs.
4 · Incompatible file formatsPrograms written in different languages can't easily read each other's files.
5 · Fixed queriesEach program does one job, so every new requirement needs a new program. Programs multiply ("proliferation").
"Some Days Don't Improve Fast": Separation, Duplication, Dependence, Incompatible formats, Fixed queries.

2.3 Why the database approach arose

The data definition was embedded in application programs, not stored separately.
+
No control over access to and changes to the data beyond what each program imposed.
→
the database
+ the DBMS

2.4 DBMS + database application program

Application programInteracts with the database by sending requests (SQL statements) to the DBMS.
⇄
DBMSSoftware that lets users define, create, maintain and control access to the database. e.g. MySQL, Oracle, SQLite (XAMPP/WAMP bundle MySQL).
⇄
Databasedata + metadata
Controlled access: what the DBMS provides
  • a security system (stops unauthorised access)
  • an integrity system (keeps data consistent)
  • a concurrency control system (lets many users share data at the same time)
  • a recovery control system (restores the database after a failure)
  • a user-accessible catalog (the metadata)
"Safe Interns Can Read Catalogs": Security, Integrity, Concurrency, Recovery, Catalog.

2.5 Views

Whole database
→
Lecturer's view
(names + grades)
Bursar's view
(names + fees)

A view is a subset of the database, so each user gets their own view.

Benefits
  • Reduce complexity (users see only what they need)
  • Provide a level of security (hide data)
  • Let you customise how the database looks
  • Show a consistent, unchanging picture even if the underlying database changes

3.3 DDL · DML · DCL and their SQL commands

DDL · Data Definition LanguageDefines the structure: data types, structures and constraints. The definitions are stored in the database (catalog). 
CREATE  ALTER  DROP  TRUNCATE  RENAME
DML · Data Manipulation LanguageWorks on the data inside the tables: query, add, change, remove. 
SELECT  INSERT  UPDATE  DELETE
DCL · Data Control LanguageControls who can do what (permissions). 
GRANT  REVOKE

SQL is a non-procedural language: you say what you want, not how to get it.

DDL = the shape of the box · DML = the stuff in the box · DCL = the lock on the box. DROP removes a table; DELETE removes rows.

3.4 The four SQL answers from last session's paper (MySQL)

-- a) create a table with 10 fields + a primary key
CREATE TABLE student (
  reg_no     INT AUTO_INCREMENT PRIMARY KEY,
  first_name VARCHAR(50),  last_name VARCHAR(50),
  gender     CHAR(1),      dob       DATE,
  email      VARCHAR(100), phone     VARCHAR(15),
  dept_id    INT,          level     INT,
  cgpa       DECIMAL(3,2)
);

-- c) add a foreign key while creating a table
CREATE TABLE department ( dept_id INT PRIMARY KEY, name VARCHAR(50) );
CREATE TABLE lecturer (
  staff_id INT PRIMARY KEY,
  name     VARCHAR(50),
  dept_id  INT,
  FOREIGN KEY (dept_id) REFERENCES department(dept_id)
);

-- b) delete multiple rows
DELETE FROM student WHERE reg_no IN (3, 5, 7);
DELETE FROM student WHERE level = 100;   -- every matching row

-- d) view all information in a table
SELECT * FROM student;

4 · The DBMS environment + roles

4.1 Five components of the DBMS environment

HardwareFrom one PC to a network of computers.
SoftwareThe DBMS, the OS, network software, and the application programs.
DataThe organisation's data, plus its description (the schema).
ProceduresThe instructions and rules for designing and using the database (DDL/DML/DCL).
PeopleNaive and sophisticated users, plus the DA, DBA, designers and programmers.

Data sits in the middle: it's the bridge between the machine side (hardware + software) and the human side (procedures + people).

"Happy Students Don't Panic Permanently": Hardware, Software, Data, Procedures, People.

4.2 Five roles in the database environment

Data Administrator (DA)Manages the data as a resource: monitors, maintains and controls the organisation's data assets and how they're used by applications and business processes. Business-side, planning.
Database Administrator (DBA)Designs, implements and maintains the database system; sets the policies for its security, maintenance and use. Technical-side.
Database DesignersLogical designers draw the ERD (what data, which relationships). Physical designers decide how it's stored (storage media).
Application ProgrammersBuild the front end (the GUI) and link it to the back end (the DBMS), using SQL.
End UsersNaive users use ready-made screens, e.g. a bank customer or teller. Sophisticated users know the database and write their own queries.
"Don't Disturb Dad's Afternoon Up-time": DA, DBA, Designers, Application programmers, Users.

LESSON 2 · THE DATABASE ENVIRONMENT

5 · The ANSI-SPARC three-level architecture

5.1 Why three levels (objectives)

  • All users can access the same data.
  • A user's view is immune to changes made in other views.
  • Users don't need to know physical storage details.
  • The DBA can change the storage structures without affecting users' views.
  • The internal structure is unaffected by changes to the physical side of storage.
  • The DBA can change the conceptual structure without affecting all users.

In one line: separate each user's view from how the data is physically stored.

5.3 What lives at each level

External = the users' viewThe part of the database relevant to one user. Different users can see the same data in different forms (e.g. a date as 27/11 or Nov 27), and can see derived data (age instead of date of birth). Users work through a GUI here.
Conceptual = the community viewWhat data is stored and the relationships among it: all entities, attributes and relationships, the constraints, and the security and integrity information. No storage details.
Internal = the physical representationHow the data is stored: storage space for data and indexes, record descriptions, record placement, data compression and encryption, on primary or secondary storage.
Go top to bottom: Each Customer Ignores the engine. External = what I see · Conceptual = what is stored · Internal = how it's stored.

Explain the diagram and what is found in each part [10]

5.4 Mappings + schemas

External/conceptual mappingTranslates between each user's view and the conceptual schema.
Conceptual/internal mappingTranslates between the conceptual schema and the internal (stored) records and indexes.

Schema = the description (logical structure) of the database, which rarely changes. Instance = the data in it at one moment, which changes all the time.

5.5 Logical vs physical data independence

Logical data independenceThe external schemas are immune to changes in the conceptual schema.
e.g. adding or removing a table or field shouldn't force changes to users' views or rewrites of application programs.
vs
Physical data independenceThe conceptual schema is immune to changes in the internal schema.
e.g. a new file organisation, storage structure or device shouldn't force changes to the conceptual or external schemas.
External  ┐
          ├─ logical independence  (protects views from conceptual changes)
Conceptual┤
          ├─ physical independence (protects conceptual from storage changes)
Internal  ┘
Each independence protects the level above the line it sits on. Logical is the upper line, physical is the lower line.

Explain the difference between logical and physical data independence [10]

5.6 Data models, DBMS functions, catalog + TP monitors

Data modelA set of concepts to describe data, relationships and constraints.
  • Object-based: ER, object-oriented
  • Record-based: relational, network, hierarchical
  • Physical: how data is stored
Typical DBMS functions
  • store, retrieve + update data
  • a user-accessible catalog
  • transaction support
  • concurrency control
  • recovery
  • authorisation (security)
  • integrity
  • data independence + utilities
NOT a function: hardware assembly.
System catalogHolds the metadata about the database: names, types and sizes of data items, constraints, users and their permissions.
Transaction Processing (TP) MonitorA program between clients and servers that manages user transactions and keeps them consistent, so large systems can handle many transactions at once.

The two-tier problem: a "fat" client needs a powerful computer, and there's a lot of client-side administration. By 1995 a third tier had been proposed.

Tier 2 · Application serverbusiness logic

⇄
Tier 3 · Database serverDBMS

Advantages

7 · ER diagram shapes + keys

7.1 What an ER diagram is

An Entity–Relationship Diagram (ERD) is a picture of a database's entities, their attributes and the relationships between them. It's used in logical (conceptual) design, before any tables are built. The textbook uses Chen notation (below).

EntityA real-world object we store data about (Student, Course). It becomes a table.
AttributeA characteristic of an entity (Name, RegNo). It becomes a column.
RelationshipHow entities are associated (a Student enrols in a Course).

7.3 The keys

   DEPARTMENT                        STUDENT
 ┌──────────┬──────┐       ┌────────┬────────┬───────┬──────────┐
 │ dept_id  │ name │       │ reg_no │ email  │ name  │ dept_id  │
 ├──────────┼──────┤       ├────────┼────────┼───────┼──────────┤
 │ 1        │ SEN  │◄──────┼────────┼────────┼───────┼─ 1       │
 │ 2        │ CYB  │       │ 241001 │ a@uni  │ Ada   │          │
 └──────────┴──────┘       └────────┴────────┴───────┴──────────┘
   primary key               primary key  candidate      foreign key
                                          (alternate)    → DEPARTMENT
Primary keyThe chosen key that uniquely identifies each row. It must be unique and NOT NULL, and there's one per table. (reg_no)
Candidate keyAny column (or minimal set) that could be the primary key. (reg_no, email)
Alternate keyA candidate key that wasn't chosen as the primary key. (email)
Foreign keyA column that refers to the primary key of another table. It links two tables. (student.dept_id → department.dept_id)
Composite keyA key made of more than one attribute. e.g. (reg_no, course_code) in an ENROLMENT table
Super keyAny set of columns that uniquely identifies a row, even one with extra columns. (reg_no + name)
Every primary key was a candidate. The losing candidates are alternates. A foreign key is someone else's primary key living in your table.
